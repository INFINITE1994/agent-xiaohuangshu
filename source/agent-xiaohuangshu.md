## 第一篇 认识智能体

### 第 1 章 智能体到底是什么

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **先说结论**：智能体（Agent）= 大模型（脑子）＋ 工具（手脚）＋ 记忆（经验）＋ 流程（习惯），它像一个"什么都会一点、但没有经验的新员工"，需要你一步步引导、限制、验收。

#### 从"大模型"到"智能体"

| 概念 | 一句话解释 | 类比 |
|------|-----------|------|
| 大模型（LLM） | 读了海量书籍、网页、代码的"超级大脑"，一个字一个字预测着说话 | 刚毕业的学霸 |
| 智能体（Agent） | 给大脑装上手脚、记忆和操作手册，能自主干活的系统 | 配齐工位的实习生 |
| API KEY | 大模型给你发的"门禁卡"，绑着账户余额，每次问答都扣钱 | 门禁卡 |
| Base URL | 给 Agent 写的"收件地址"，告诉它把请求发到哪个服务器 | 寄信地址 |
| Skill | 教 Agent"遇到某件事该怎么做"的说明书 | 标准菜谱 |
| MCP | Agent 和外部工具之间的"USB 接口标准"，工具即插即用 | USB 插口 |
| 多模态 | 不光读字，还能看图、听声、看视频的模型 | 五官齐全 |

> **小白注**：后文看到这几个词时，可以这样翻译——**Token** = AI 按字数收费的单位（大约 1 个汉字 ≈ 1–2 个 token）；**终端 / CLI** = 那个打命令的黑窗口（Win+R 输入 cmd 回车就能打开）；**沙盒** = 给智能体围的"儿童围栏"，围栏外它碰不到。更多词见附录 D「小白术语表」。

**为什么 Agent 要接入大模型？** 大模型是 Agent 的"脑子"——没有它，Agent 只是个按固定脚本办事的木偶；接上之后，它才能看懂需求、拆解任务、自己决定什么时候调用什么工具。

#### 最重要的心法：把它当实习生

> 智能体能帮你解决大多数问题，但**不能解决所有问题**。他不是神，是实习生：需要你一步步引导、限制、验收，而不是当甩手掌柜。判断不了结果对不对的任务，就不要让它独立完成。

#### 新手高频问题速答

| 问题 | 答案 |
|------|------|
| 为什么我的智能体不能识别图片？ | 你接的是纯文本模型而不是多模态模型，换多模态模型即可 |
| 为什么它老是说英文？ | 直接对它说："以后所有回答都用中文。" |
| 为什么我的智能体这么笨？ | 大概率是没装 Skill——没技能的新员工当然笨（见第 3 篇） |
| 为什么它老是出错/乱删文件？ | 多半是因为开了"完全访问"权限。权限给最小化（见第 6 篇） |
| 为什么本地部署的模型很卡？ | 模型参数超过硬件能力，或没做量化优化。直接说"我的本地模型很卡，帮我优化" |
| 怎么选模型？ | 按任务选：DeepSeek 强于数学推理、GLM 强于代码、Kimi 强于文学长文、豆包强于语言与生图 |
| 如何省 Token？ | 普通任务用免费/低价模型（小米、豆包、GLM、Kimi），复杂任务再切强模型 |

#### 智能体能帮你做什么

数据分析、写代码、设计前端、做 PPT、整理电脑、对接电商、解决电脑问题……入门建议先做两个小任务：① 按一份方案生成公司介绍 PPT；② 生成一个博客网站完整页面。做完你就知道"实习生"的能力边界了。

> **记住这点就够了**：智能体是配齐工具和经验的大模型实习生——你教它、管它、验收它，它就真能替你干活。

### 第 2 章 AI 编程工具进化史与 2026 格局

> **小白提示**：本章是"行业新闻"，赶时间可以先跳过，等装好智能体再回来看。

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **大白话讲**：AI 编程工具五年变了四次——从"帮你补代码"进化到"帮你交付任务"；2026 年选工具看定位：Claude Code 像终端里的长期搭档，Codex 像 OpenAI 生态的多端工程 Agent，国产工具负责便宜好用。

#### 四次进化

| 阶段 | 时间 | 代表 | AI 的角色 |
|------|------|------|----------|
| 补全时代 | 2021 | GitHub Copilot | 更聪明的输入法：你写开头，它补后面 |
| 对话时代 | 2022 | ChatGPT | 问答伙伴：复制代码、粘贴报错、要答案 |
| 项目协作时代 | 2023–2024 | Cursor | 编辑器里的协作者：看文件、改函数、跨文件重构 |
| 工程 Agent 时代 | 2025–2026 | Codex、Claude Code、Hermes | 工程执行者：读项目→计划→改代码→跑命令→整理 PR |

记住这点：**Copilot 帮你补代码，ChatGPT 帮你想代码，Cursor 陪你改项目，Codex / Claude Code 帮你执行工程任务。**

#### 主流工具怎么选（2026-08 更新版）

| 工具 | 一句话定位 | Windows 体验 | 2026 年 8 月状态 |
|------|-----------|-------------|-----------------|
| Claude Code | 终端里的长期工程搭档，生态最成熟 | 原生 | v2.1.22x，跨会话通信、Routines、动态工作流； 社区报告 2.1.91–2.1.196 有后门风险，务必官方源安装并保持最新 |
| Codex | OpenAI 生态的多端工程 Agent | 官方桌面应用 | 已并入 ChatGPT 桌面 App：Chat（讨论）/ Work（交付成品）/ Codex（操作文件）三入口；GPT-5.6 三档模型 |
| Hermes | 开源协作型智能体，会自行进化 | Desktop 公测 | v2026.4.x，开发商估值约 15 亿美元 |
| Deveco Code（华为） | 鸿蒙开发 + 通用 Vibe Coding | | 开源免费，内置 GLM-5.4 和小米模型，安全审计出色（9 分） |
| ZCode（智谱） | 基本可平替 Codex | | 每天送 300 万 GLM-5.2 token |
| Trae（字节） | IDE 编码工具 | | 国内免费，热门模型需排队 |
| WorkBuddy | 应用内技能包，一键安装 | | 适合轻量办公，不适合大型开发 |

**Codex 与 Claude Code 的区别：**

- Claude Code 更像**终端里的长期协作搭档**：长读项目、持续追踪复杂任务、边讨论边修改，适合终端工作流；
- Codex 更像 **OpenAI 生态里的多端任务执行平台**：App/CLI/IDE/Web 四个入口切换，配合 ChatGPT 账号体系、GitHub PR 工作流、Skills 与插件生态；
- 两者没有绝对谁替代谁，最终看：模型能力、上下文处理、工具链、价格、团队习惯。

#### 2026 年 7–8 月的重大变化：Codex 并入 ChatGPT

- **7 月中旬**：OpenAI 把 Codex 桌面 App 和 ChatGPT 桌面端合并，旧聊天界面改名 **ChatGPT Classic**；后因社区吐槽，"ChatGPT Codex" 又改回 "Codex"；
- 新 App 三个岗位：**Chat 负责讨论、Work 负责交付成品、Codex 负责操作项目**——口诀：**要答案用 Chat，要成品用 Work，要动文件用 Codex**；
- **7 月 9 日 GPT-5.6 发布三档模型**：Sol（旗舰，$5/$30）、Terra（均衡，GPT-5.5 性能一半价格）、Luna（最便宜最快，长文弱）；另有 Sol Ultra 高算力模式（默认并行 4 个子智能体，最高 16 个）；
- **额度规则**：Codex / Work / ChatGPT for Excel / Workspace Agents **共享同一套 Agent 额度**；普通 Chat 走聊天额度（如 Plus 每 3 小时 160 条）——所以"Chat 聊方案、Codex 干执行"是省钱根本；
- 模型选择口诀：**默认 Terra，简单 Luna，关键才用 Sol**。

> **说白了就是**：先想清楚要用智能体做什么，再选工具；2026 年"选工具"的本质是"选生态"——深度用哪家就住进哪家。

### 第二步：安装 Git（Windows 小白版）

1. 下载：https://git-scm.com/download/win ，点页面中部灰色卡片 **"Standalone Installer — Git for Windows / x64 Setup"**；
- 不点 "Portable"（绿色版易出问题）；不点 "ARM64"（特定电脑专用）；
2. "选择目标位置"那一步：**确认路径是 `C:\Program Files\Git` 后直接 Next，不要改路径**；
3. "Choosing the default editor"那一步：确认 Nano 默认选中，直接 Next；
4. 其余全默认。验证：`Win+R` → `cmd` → 输入 `git --version`，显示 `git version 2.xx.x.windows.1` 即成功。

> **怎么算装对了**：看到 `git version 2.xx.x.windows.1` 就是成功。
> **常见报错**：提示"不是内部或外部命令"→ 说明当前窗口是安装前打开的，**关掉黑窗口重新打开一个**再试；还不行就重启电脑。

#### 第三步：安装 Node.js

1. 下载：https://nodejs.org/zh-cn/download/ ，点左侧 **LTS** 的 `.msi`（ 不点右侧 Current）；
2. 到 "Custom Setup" 界面**确认勾选 "Automatically install the necessary tools"**（默认已勾，别取消）；

### 第 6 章 Codex 安装与上手

> 难度：入门 ｜ 更新时间：2026-08-14

#### 认识 Codex：从代码补全到工程 Agent

Codex 不是"又一个写代码的 ChatGPT"，而是能进入项目、读文件、理解上下文、定计划、改代码、跑命令、整理 PR 的**工程执行者**。它适合：目标明确、范围可控、结果能验证、失败能回滚的任务；不适合：生产数据库、支付核心、大规模迁移等你自己都验收不了的任务。

#### App 安装与上手（新手最推荐）

1. 官方页面下载 Windows/macOS 版（Mac 按芯片选 Apple Silicon 或 Intel，别选错）；
2. 第一次打开：登录 → 选**项目目录**（ 选一个干净的练习目录，不要 C 盘根目录、不要重要项目）；
3. 理解三个核心概念（类比表）：

| 概念 | 简单来说 |
|------|---------|
| 项目（Project） | 一个代码文件夹 = 一家公司 |
| Thread | 项目里的一个任务对话 = 一个员工（一个任务开一个 thread，别全塞一起） |
| Review Pane / Diff | "作业检查区"——绿色新增、红色删除，**每次完成先看 diff，再看它的总结** |

> **小白注**：**diff** = 智能体改动的"前后对照表"：绿色行 = 新加的，红色行 = 删掉的。看不懂就全选复制，问它："用大白话解释你改了什么。"

4. 推荐第一个任务：`请帮我做一个简单网页：黑色背景，中间显示 Hello, Codex，字体白色，水平垂直居中，只使用 HTML 和 CSS`；

**沙盒权限（保命核心）：**

| 权限选项 | 与沙盒的关系 | 建议 |

| 请求批准 | 有围栏，越界操作先问你 | 新手推荐 |

| 完全访问权限 | 放开围栏，可执行任何操作 | 新手不要开 |

**推理强度四档：** 低（改文案/改颜色，省额度）→ 中（日常开发，默认）→ 高（复杂 bug、重构）→ 超高（架构分析、反复修不好的 bug）。**不要所有任务都开最高。**

**计划模式：** 复杂任务先开计划模式（或输入 `/plan`）——让 Codex 先出工作计划，你确认后再动手，能查漏补缺。

### 第 9 章 Skill 是什么、为什么

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **先给你交个底**：Skill 就是写给 AI 的"标准菜谱"——说清楚什么时候用、怎么做、做完交出什么；没有 Skill 每次从零摸索，有了 Skill 按成熟方法来。

#### 标准菜谱的比喻

你开了个餐厅，雇了个新厨师。你不能每次都手把手教他做菜，所以你写了一份**标准菜谱**：什么时候做、用什么料、按什么步骤、出什么成品。Skill 就是写给 AI 的"标准菜谱"。

一份合格的 Skill 包含三样东西：

1. **什么时候用**：如"当用户说要做视频的时候"。智能体靠这段判断要不要翻开说明书；
2. **具体怎么做**：第一步干什么、用什么工具、参数设多少——越具体越好；
3. **容易出什么错**：哪些操作会搞砸、怎么避免、怎么修——这部分是经验，比步骤更值钱。

#### 三个常见误区（新手必看）

| 误区 | 真实情况 |
|------|---------|
| Skill 就是写个提示词 | 不对。提示词是"临时对话"，Skill 是"可反复使用的标准流程"——"今天帮我炒个菜" vs "写一本标准菜谱" |
| Skill 要写得详细复杂 | 不对。越简洁越聚焦执行越好——菜谱写 3 页没人看，写 1 页步骤清晰才是好菜谱 |
| Skill 要解释"为什么" | 不用。Skill 是"下命令"不是"写论文"，AI 只需要知道怎么做 |

#### 没有 Skill vs 有 Skill

| 没有 Skill | 有 Skill |
|-----------|---------|
| 每次都要重复交代（分辨率、帧率、工具都要重说） | 不用重复交代，说一句它自己知道怎么做 |
| 容易犯同样的错（这次纠正了下次还犯） | 注意事项写在里面，每次执行前都会看 |
| 质量忽高忽低（每次方法可能不一样） | 步骤固定、参数固定、质量稳定 |
| 经验带不走 | 可以分享给同事，装上就能用 |

> **记住这个**：Skill 是智能体的操作说明书，是"有经验的助理"和"新来的助理"的区别。

#### 插件、Skill、MCP 三者关系（先记这张表）

### 第 11 章 怎么找、怎么判断一个好 Skill

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **抓重点**：先想清楚你反复交代的是什么，再去平台和社区找；判断好坏看五条：描述清、有踩坑、步骤具体、更新勤、评价好。

#### 第一步：想清楚你要解决什么问题

你经常让智能体做的事是什么？哪些事每次都要重复交代？哪些事它总做不好？想清楚再找。

GitHub 搜 "ai agent skill"、"claude code rules"、"codex agents.md"；Reddit、V2EX、掘金、抖音都有大量推荐。

#### 判断一个 Skill 好不好的五条标准

| 判断点 | 好 Skill | 差 Skill |
|--------|---------|---------|
| 描述清不清楚 | 写清"什么时候用、能干什么" | 描述模糊（"通用工具"） |
| 有没有踩坑经验 | 有"注意事项/常见问题"（作者真用过） | 没有踩坑部分，实用性存疑 |
| 步骤具体不具体 | 具体命令、具体参数 | 只写"用 XX 工具处理" |
| 更新频率 | 近期有更新（尤其涉及 API/工具版本） | 半年没动，可能已过时 |
| 评价和使用量 | 下载量高、评价好 | 无评价数据 |

> **实操要点**：找 Skill 先问自己"我在反复教它什么"；选 Skill 先看"注意事项"——有踩坑经验的才可信。

### 第 12 章 怎么写自己的 Skill

> 难度：进阶 ｜ 更新时间：2026-08-14
>
> **最核心的一点**：写 Skill 的关键三点——描述清楚什么时候用、步骤具体到命令、把踩坑经验记下来；先让它能跑通，再慢慢完善。

#### 什么时候该写

1. **你重复教过它三次以上**——每次都交代工具、参数、格式，写成 Skill 一劳永逸；
2. **它犯了一个你觉得不该犯的错**——纠正后写进注意事项，它就不会再犯；
3. **你有一个多步骤工作流程**——如"写文案 → 做幻灯片 → 抓帧 → 合成视频"，写成 Skill 不漏步骤；
4. **你的项目有特殊规范**——"注释用中文""commit 用 Conventional Commits"等，写成项目级 CLAUDE.md / AGENTS.md。

#### 通用模板

```markdown
## 标题（做什么事）

### 什么时候用
- 触发条件 1：用户说「XXX」
- 触发条件 2：用户要做 XXX
- 不要用的场景：XXX

### 环境和工具
- 需要安装什么：XXX
- 需要什么权限：XXX
- 用什么工具：XXX

### 操作步骤
1. 第一步：具体做什么，用什么命令
2. 第二步：具体做什么，参数设多少

### 注意事项（踩坑经验）
1. 不要做 XXX，因为会 YYY
2. 一定要做 XXX，否则会 YYY
3. 如果遇到 ZZZ 错误，用 WWW 方法解决

### 验证结果
- 检查 XXX 是不是正确
- 跑一遍 XXX 确认没问题
- 预览一下最终效果
```

#### 真实例子：项目级规范（CLAUDE.md / AGENTS.md）

```markdown
# 项目规范

## 技术栈
- Python 3.11
- FastAPI + SQLAlchemy
- pytest 测试框架

## 代码风格
- 注释用中文
- 变量名用英文驼峰
- 函数名用英文下划线
- 每个函数必须写 docstring

## 提交规范
- commit message 用英文
- 格式：type: description（如 feat: add user login）
- type 只能是 feat/fix/docs/refactor/test/chore

## 测试要求
- 新功能必须写单元测试
- 测试文件放在 tests/ 目录
- 运行命令：pytest tests/ -v

## 注意事项
- 不要修改 alembic/ 下的迁移文件
- 不要在 main.py 里写业务逻辑
- 数据库密码必须从环境变量读取
```

放在项目根目录，智能体每次启动都会读，写代码时自动遵守。（Codex 里可以用 `/init` 生成，也可以直接对它说"把项目初始化成 AGENTS.md"。）

#### 写好 Skill 的 5 条核心原则

1. **名字要准确**——小写字母 + 连字符： `running-tests` `test-helper`；
2. **只做一件事**——一个 Skill 只管一件事，想要多个能力就写多个；
3. **说清"什么时候用/不用"**—— "当用户要求跑单元测试或执行 pytest 时使用；只是问概念时不使用" "用于测试相关场景"（AI 会乱猜）；
4. **步骤具体到能直接执行**——不写"适当处理"： "运行 `pytest --tb=short`；返回码非 0 则提取最后 20 行错误；输出通过数/失败数/失败用例名" "运行测试、检查结果、给出报告"；
5. **写清楚"出错怎么办"**——找不到文件、超时、权限不足分别怎么回复，异常覆盖才是高手。

#### 该管多松多紧？

| 任务类型 | 管多紧 | 举例 | 怎么写 |
|---------|-------|------|--------|
| 创造性任务 | 松一点 | 写代码审查意见、写文章 | 给方向和原则 |
| 半固定任务 | 中等 | 生成报告、写周报 | 给模板结构，内容可灵活 |
| 不能出错的任务 | 管死 | 数据库迁移、部署上线 | 每步写死命令 |

> 就像带小孩：画画课随便画（松），做数学题按公式（中），过马路必须牵手（紧）。

#### 从零写一个 Skill 的完整流程

**先让 AI 裸干一次 → 记录哪里翻车 → 写最小 Skill → 测试验证 → 慢慢补充完善**

1. **先不写，让 AI 直接干一次**：记录哪里不好——理解错需求？步骤乱？格式不对？
2. **设计 3~5 个测试场景**：每个场景写清"输入什么、期望输出什么"，这就是以后的"考卷"；
3. **写最小版本**：只写能解决翻车问题的规则，先跑通；
4. **拿"考卷"验证**：没通过继续改；
5. **逐步补充边界**：空输入怎么办？文件不存在怎么办？

> **先让它能用，再让它好用**。不要一上来就追求完美。

#### 聪明人的做法：让 AI 帮你写

1. 先让它干一遍活（正常对话完成一次真实任务）；
2. 让它复盘："你刚才做了哪几步？""哪些是每次都要做的固定流程？""哪些地方你不太确定？""什么情况下不该用这个流程？"
3. 把复盘结果整理成 SKILL.md（Codex 里直接用 `$skill-creator`，它会问你用途/触发场景/输出格式/限制并生成）；
4. 测试、调整、再测试。

> 就像：让员工自由发挥干一次 → 让他总结 → 你帮他写成标准流程 → 以后所有新员工照着做。

#### 新手避坑清单

| 坑 | 为什么是坑 | 怎么避免 |
|----|-----------|---------|
| 用 Windows 路径 `C:\xxx\` | 换系统就炸 | 统一用 `xxx/yyy/` 格式 |
| 给太多选择 | AI 不知道选哪个，结果不稳定 | 直接指定："默认用 PostgreSQL" |
| 写入会过期的信息 | 如"2026 年 5 月前用旧 API" | 过期信息放单独文件，标注"已废弃" |
| 同一个东西叫不同名字 | 一会儿"接口地址"一会儿"API URL"，AI 混乱 | 全文统一一个名称 |
| Skill 写得像论文 | AI 不需要知道"为什么" | 删掉解释性文字，只留操作指令 |
| 一个 Skill 干太多事 | 经常丢步骤或搞混 | 拆成多个 Skill |

> **核心别丢**：写 Skill 不是高深技术——把你会的事情写成 AI 能照着做的说明书。你能教会一个新员工，就能写出一个好 Skill。

### 第 13 章 完整示例与文件组织

> 难度：进阶 ｜ 更新时间：2026-08-14
>
> **先定个调**：一个完整 Skill = 一个文件夹 + 一个 SKILL.md（≤500 行），长资料拆进 references/；写好 description 让 AI 自动判断何时调用。

#### 完整示例：自动整理下载文件夹

```markdown
---
name: organize-downloads
description: "整理下载文件夹。当用户说'整理下载'、'清理下载文件夹'时触发。"
---

## 什么时候用
- 用户说"整理下载"、"清理下载文件夹"、"帮我归类下载的文件"

## 什么时候不用
- 用户只是问"下载文件夹在哪里"（只问位置，不需要整理）

## 输入
- 下载文件夹路径（默认 ~/Downloads）

## 输出
- 整理报告：移动了多少文件、每个类别有多少个

## 具体步骤
1. 扫描下载文件夹里所有文件
2. 按文件类型分类：
- 图片（.jpg .png .gif .webp）→ 移到 ~/Downloads/图片/
- 文档（.pdf .doc .docx .txt）→ 移到 ~/Downloads/文档/
- 视频（.mp4 .mkv .avi）→ 移到 ~/Downloads/视频/
- 压缩包（.zip .rar .7z）→ 移到 ~/Downloads/压缩包/
- 其他类型 → 保持不动
3. 如果目标文件夹不存在，先创建
4. 如果目标位置已有同名文件，在文件名后加日期后缀
5. 输出整理报告

## 出错怎么办
- 文件正在被占用 → 跳过，报告中注明"跳过（被占用）"
- 权限不足 → 跳过，报告中注明"跳过（无权限）"
- 移动失败 → 不删除原文件，报告中注明失败原因
```

注意看这个示例：名字准确、描述有触发词、"用/不用"写清、步骤能直接执行、错误也覆盖了——这就是合格 Skill。

#### Skill 文件怎么放

```
skills/
organize-downloads/
SKILL.md # ← 主文件，必须有
running-tests/
SKILL.md
references/ # ← 补充资料（可选）
pytest-cheatsheet.md
scripts/ # ← 可选脚本
assets/ # ← 可选模板/资源
```

- 每个 Skill 一个文件夹，文件夹名 = Skill 名；SKILL.md 放核心内容（建议 ≤500 行）；
- 长资料放 `references/`，AI 需要时自己去读——这就是 2026 标准的**渐进式披露**：主文件精简，细节拆出去；
- 放置位置：项目内 `.agents/skills/`（项目专属）→ 用户级目录（个人通用）→ 插件（打包分发）。

#### 怎么让它"自动学习"

- Hermes 等有"自动保存 Skill"功能：纠正一次，它自动保存，下次直接用；
- 没有这功能就手动：① 发现做错 → 告诉它"应该 XXX"；② 说"把这个经验保存下来，以后遇到同样的事直接用"；③ 下次验证有没有用上，没用上就检查 Skill 是否被正确加载。

### 第 14 章 需求与方案

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **一句话概括**：需求大多来自"老板拍脑袋、产品抄竞品、用户骂娘"；开发的两件保命事——评审会上问清异常流程，估时间永远留 buffer。

#### 新人常见幻觉 vs 现实

| 幻觉 | 现实 |
|------|------|
| 需求文档会很详细吧？ | 很多公司 PRD 就是几张截图加几句话 |
| 写好代码就能上线吧？ | 中间还有联调、测试、改 bug、再测试，循环 N 次 |
| 测试会把 bug 都发现吧？ | 线上 bug 永远存在，只是看影响大不大 |
| 上线就是点一下按钮吧？ | 可能点完按钮全公司熬夜救火 |

#### 评审会：两个核心任务

1. **估时间**：产品说"很简单，就加个按钮"，你得脑补背后要改几张表、几个接口、多少页面；
2. **挑毛病**：PRD 没写异常流程？问。没写兼容方案？问。没写数据统计？问。**评审会上不问，以后就是你加班补。**

**估时间的潜规则：**

- 产品给的 deadline 不能当真，按"正常干完 + 联调 + 改 bug"报；
- 你说 3 天，产品和项目经理记成 2 天——报 5 天留 buffer；
- 不当面说"做不了"，要说"可以做，但需要 X 天 / 砍掉 Y 功能"。

#### 需求变更应对

| 变更类型 | 应对 |
|---------|------|
| 小改动（文案、样式） | 口头答应顺手做，但**在群里留痕**，防扯皮 |
| 大改动（逻辑、功能） | 让产品重新发 PRD/变更单，重新评估工期："能做，但上线时间延后" |
| 临上线改需求 | 除非老板亲自下令，否则一律拒绝——这叫**封版**，是保命底线 |

> 血泪教训：有同事上线前夜答应改"小逻辑"，牵一发动全身，回滚 3 次通宵到早上 6 点。从此团队规定：**封版后只修 P0 bug，其余一律下版本。**

#### 最小化技术方案（写不写？）

- 大厂必须写方案文档、架构师点头才开工；小厂"先写吧，边写边想"是常态——但你不写，后面联调、交接、线上出问题时就得背锅；
- 最少落到文档/备注这四点：① 改哪些接口/页面，影响范围？② 数据库加字段/表？要不要迁移？③ 依赖哪些第三方？挂了怎么办？④ 并发/性能/安全风险怎么处理？

> 反面教材："积分抵扣"没考虑并发，两人同时下单积分被扣两次。根因：没写方案，没意识到扣积分不是原子操作。

> **最后敲个黑板**：需求阶段的核心不是"接活"，是"问清楚 + 留 buffer + 留痕"。

### 第 15 章 开发、联调与 Code Review

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **浓缩成一句**：编码期四件事——别裸奔、日志记清、异常别吞、密钥别硬编码；Git 用不好轻则丢代码重则搞崩主分支；联调先对文档，CR 先自己 diff 一遍。

#### 编码期间注意点

- **别裸奔**：至少自测 happy path（主流程能跑通），别写完就扔给测试，会被鄙视；
- **日志记清楚**：关键节点打日志；但别到处 print，线上日志太多会被运维骂；
- **异常别吞掉**：try-catch 至少打 error 日志，别直接 pass——否则线上出事时日志干干净净，你根本不知道怎么死的；
- **敏感信息别硬编码**：密码、密钥、token 放环境变量，代码会被所有人看到。

#### Git 使用规范（保命用）

- 每天下班前 push，哪怕没写完——硬盘挂了哭都来不及；
- 提交信息写人话： `fix: 修复优惠券重复领取时库存扣减异常` "fix bug"；
- 合并前先 pull 最新主分支，解决完冲突再提交；
- **永远不要在主分支上开发；永远不要 force push。**

```
feat: 新增XX功能
fix: 修复XX问题
refactor: 重构XX逻辑（没有改功能）
chore: 配置、构建相关改动
```

#### 联调：最痛苦的环节

**为什么痛苦：** 字段名不一致（userId vs user_id）、类型对不上（整数 vs 字符串）、接口没好（"明天好"→"下午好"→"晚上好"）、环境不通。

**减少痛苦四招：** ① 先对文档（Swagger/Apifox/YApi 落全参数与错误码）；② 后端没写好前端先 Mock，别傻等；③ 提前定规范（驼峰 vs 下划线、空值传 null 还是不传）；④ 环境挂了别硬扛，一起找运维。

**联调暗语翻译：**

- "接口好了" = 主干逻辑通了，边界情况没测；
- "你先看下" = 可能有 bug，但我还没自测；
- "这个数据不对吧" = 大概率是你传错了，但你不好直说。

#### Code Review：在审什么、怎么应对

| 审什么 | 要点 |
|--------|------|
| 逻辑对不对 | 空指针、边界条件、并发安全 |
| 命名清不清楚 | a、b、c 这种变量名直接打回 |
| 有没有冗余 | 同样逻辑写三遍就抽公共方法 |
| 安全隐私 | SQL 注入、输入校验、敏感信息脱敏 |

**应对：** 明显对的乖乖改；觉得不合理的可以讨论但语气要好（"这里我这样做是因为 XXX，你觉得呢？"比"你不懂"强一万倍）；一次被提 50 条别崩溃，分优先级改。

**CR 避坑：** 提交前自己先 diff 一遍；描述写清"改了什么、为什么改、怎么验证的"；别在 CR 里做需求变更。

> **小结一下**：代码是写给人看也写给 AI 看的；日志、Git、文档是你的"护身符"，别省。

### 第 16 章 测试与上线

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **掏心窝说一句**：QA 是你这期间的"敌人"，也是帮你挡子弹的人；上线前必过 checklist、必想好回滚方案；上线后至少观察 30–60 分钟。

#### 测试四板斧

| 类型 | 测什么 |
|------|--------|
| 功能测试 | 对着 PRD 一条一条过 |
| 边界测试 | 空输入/超长/并发点击——最容易出 bug |
| 兼容性测试 | 不同浏览器/机型/系统——前端最头疼 |
| 回归测试 | 改一处测周边，防止改 A 坏 B |

**Bug 生命周期：** 测试发现 → 提 bug 单（复现步骤、截图、期望、实际）→ 开发确认修复 → 状态改"已修复" → 测试复测关闭 / 不通过重开。误报可以拒绝，但要有理有据。

**和测试相处的原则：**

- 不说"我这边是好的"，要说"我在 XX 环境复测了，确实没问题"；
- 不私下改 bug 不更新单子——测试不知道你改了不会复测；
- 复现不了厚着脸皮当面看，别硬扛；
- 提测前自己先跑一遍主流程；bug 当天响应；修完告知验证入口。

#### 上线前 checklist

- [ ] 代码已合并到发布分支且最新
- [ ] 配置已配好（数据库连接、第三方 key、开关）
- [ ] 数据库变更脚本已在预发布环境跑过
- [ ] **回滚方案明确**
- [ ] 产品/测试已知会，有人值班

#### 三种发布方式

| 方式 | 适用 | 说明 |
|------|------|------|
| 直接发布 | 小功能、低风险 | 直接全量，小厂常见 |
| 灰度发布 | 常规功能 | 先 1%/5%/10% 观察，最稳妥 |
| 蓝绿部署 | 关键服务 | 新旧两套环境，验证后切流量，出问题秒切回 |

**上线当晚：** 盯监控大屏、每 5 分钟刷错误率、产品问"好了吗"你说"再观察 10 分钟"、发现异常**第一时间回滚**，别想着热修复。

**上线后：** 观察 30–60 分钟核心指标 → 产品/运营验收 → 次日复盘；有问题写事故报告。

> **浓缩一句**：测试是帮你挡子弹的；上线最贵的不是发布，是"回滚方案"。

### 第 17 章 救火与复盘

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **开门见山**：线上问题处理顺序永远是"先止血，再看病"——能回滚就回滚，日志是你的命根子。

#### 故障分级

| 级别 | 定义 | 处理要求 |
|------|------|---------|
| P0（致命） | 核心功能不可用/数据丢失/资金安全 | 立刻回滚/热修，全员 oncall |
| P1（严重） | 主要功能异常，有绕过方案 | 2 小时内修复或回滚 |
| P2（一般） | 非核心功能异常 | 下个版本修 |
| P3（轻微） | UI 问题、文案错误 | 有空再说 |

#### 处理流程五步

1. **发现**：监控告警、用户投诉、客服反馈；
2. **止损**：能回滚就回滚，不能就降级/关开关，先恢复服务；
3. **定位**：查日志、查链路、复现，找根因——**日志是你的命根子**；
4. **修复验证**：修完观察一段时间再算结案；
5. **复盘**：写事故报告（时间线、根因、改进措施）——不是批斗会，是为了下次不犯。

**日志基本功：** 会按时间段/关键字/用户 ID 搜日志；知道日志存哪（文件/ELK/阿里云 SLS）；学会看链路追踪（SkyWalking、Jaeger）。

#### 各角色到底在干什么

| 角色 | 核心工作 | 你打交道时 |
|------|---------|-----------|
| 产品经理 | 提需求、定优先级、验收 | 需求不明确找他对 |
| 项目经理 | 排期、催进度、协调资源 | 周报日报发给他，延期提前说 |
| 测试工程师 | 写用例、测功能、提 bug | 别吵，bug 修完主动告知 |
| 前端/后端 | 写页面/写接口 | 接口文档给清楚，字段别偷改 |
| 运维/SRE | 部署、监控、报警 | 上线前要环境权限，告警别静音 |
| 设计师 | UI 稿、切图、走查 | 实现差距大提前沟通 |

> 小公司一人身兼数职，大厂分工细但沟通成本高，各有好坏。

#### 给新人的生存建议

- 日报/周报及时写，哪怕只写"开发 XX 功能，联调中"——领导看不到进度会慌；
- 开会做笔记、会后发纪要——口说无凭，记录是甩锅神器；
- 不懂就问，但先自己搜；同样的问题别问三遍；
- 接任务先复述："我理解是要做 XX，对吗？"
- 别在群里 @老板问技术细节；别封版后偷偷改代码；**别说"应该没问题"——那是线上故障的预言**，要说"我验证过了，在 XX 环境正常"。

> **带走这一句**：流程是死的，人是活的——保持沟通、留好记录、该甩锅时别怂，该背锅时别躲。

### 第 18 章 智能体开发六步法（企业级）

> 难度：进阶 ｜ 更新时间：2026-08-14
>
> **核心就在这**：智能体不是"写个 Prompt 调个接口"就完事——它必须靠"评测 + 日志 + 监控"三位一体约束；上线前：评测集通过率 ≥ 90%、核心场景零阻塞、安全过滤生效。

#### 六步标准流程

| 步骤 | 做什么 | 关键产出 |
|------|--------|---------|
| 1 需求澄清 | 明确目标（客服/生成/分析/自动化）；交互方式（同步/异步）；**"必答清单"和"必须拒绝的场景清单"**；合规确认 | 场景定义文档 |
| 2 技术选型 | 选基座模型（GPT-5.6/Claude/DeepSeek/GLM-5/Kimi K3）；系统提示词 + Git 版本管理；工具 schema；记忆策略（N 轮/摘要/向量）；异常降级 + 内容安全层 | 架构设计 |
| 3 测试集构建 | 收集 100+ 条真实 query（高频/低频/边界）；标注理想回答/必含信息点/禁止内容；自动化评测脚本（规则或 LLM-as-a-Judge）；**每次改 Prompt 必须全量回归** | 评测集 |
| 4 开发实现 | Prompt/工具/记忆/后处理模块化；全链路日志（输入/上下文/原始输出/耗时）；SSE 流式 + "停止生成"按钮；QPS 限流与熔断 | 可维护代码 |
| 5 联调验收 | 与产品对齐语气/格式/统一"不知道"话术；测试集跑分写入验收报告（通过率 + 阻塞项）；配置调用成功率/延迟/Token 告警阈值 | 验收报告 |
| 6 上线迭代 | 灰度 1%/5% → 全量；收集点赞/点踩/纠错回流优化；A/B 实验决定 Prompt/模型/Temperature | 持续优化 |

> **骨子里的道理**：传统代码靠测试兜底，智能体靠"评测集 + 日志 + 监控"三件套兜底——不确定性越高，流程越要死板。

### 第 19 章 标准工作流与提示词模板库 

> 难度：进阶 ｜ 更新时间：2026-08-14
>
> **先说结论**：标准工作流 = 需求拆解 → 计划 → 小步实现 → 测试 → 审查 → 提交复盘；好 Prompt 有四个要素——目标、上下文、输出格式、边界条件；本模板库可直接复制使用。

#### 为什么需要标准工作流

直接一句"帮我做一个网站"不是不行，但 AI 改得很快，你不知道它改了什么、能不能交付。稳定方式：**先计划，后执行；一次只改一小块；每一步都可验证。**

#### Prompt 四要素（OpenAI 官方 2026 指南）

| 要素 | 回答的问题 | 示例 |
|------|-----------|------|
| Goal（目标） | 应该做什么？ | "把会议记录整理成项目进展通报" |
| Context（上下文） | 哪些信息有帮助？各资料干什么用？ | "按品牌手册语气写；旧销售报告只用于了解客户，不引用过期数字" |
| Output（输出） | 什么格式、长度、详细度？ | "一页摘要，决策和下一步放最前" |
| Boundaries（边界） | 哪些不能动？哪些要先确认？ | "不要改金额和日期；只生成草稿不要发送" |

> 边界条件别写太多——选一两条"最容易造成实际损失"的写死即可。

#### 标准六步法 + 每步模板

**第 1 步：需求拆解（先别改代码）**

```
请先帮我做需求拆解，不要立刻修改代码。
需求：【这里写你的需求】
请按下面结构分析：
1. 背景是什么（项目阶段 / 为什么要做 / 属于新功能、Bug 修复、UI 优化还是重构）
2. 要解决什么问题（具体到什么程度 / 哪些不在本次范围）
3. 哪些文件可能相关（先列出来，不要直接修改）
4. 哪些功能不能动（不要改哪些逻辑、接口、页面、组件、依赖）
5. 什么结果算完成（功能/页面/代码的完成标准）
6. 需要哪些测试（运行什么命令 / 手动检查哪些页面 / 重点验证哪些流程）
7. 有哪些风险（影响范围 / 样式污染 / 重构过度 / 新增依赖）
最后给我一个简短执行建议：先做哪一步，是否需要我确认后再修改。
```

**第 2 步：制定计划**

```
先不要写代码，也不要修改任何文件。
请根据当前需求和项目结构，制定一个修改计划。等我确认后再开始执行。
```

（Codex 里可用 /plan；Claude Code 里切换 Plan Mode。）

**第 3 步：小步实现（一次只改一个功能点）**

```
请开始小步实现。当前只执行第【1】步：【这里写本次只做的一个功能点】
要求：
1. 一次只改这个功能点
2. 只修改和当前功能直接相关的文件
3. 不要顺手重构无关代码、不要改目录结构
4. 不要新增不必要依赖、不要删除已有功能
5. 不要改计划外的文件
修改完成后停止，并输出：
1. 本次修改了哪些文件 2. 每个文件改了什么 3. 为什么必要
4. 有没有改到计划外内容 5. 有没有潜在风险 6. 下一步建议
如果遇到不确定的地方，请先停下来问我，不要自行决定。
```

**第 4 步：测试（用结果证明，不是听它说"完成"）**

```
请对本次修改进行测试，不要继续新增功能。
请按顺序执行或说明：
1. 单元测试（有则运行，失败说明原因）
2. 类型检查（有无 typecheck 命令）
3. lint（区分本次新增问题和项目原有问题）
4. 构建（失败请说明报错和影响范围）
5. 手动测试（列出页面、操作步骤、每一步预期结果）
6. 浏览器测试（显示 / 控制台报错 / 移动端 / 关键交互）
7. 回归测试（本次修改是否影响旧功能，列出可能受影响的页面组件）
最后输出：哪些通过 / 哪些失败 / 失败原因 / 能否进入下一步。
```

**第 5 步：代码审查（两轮：AI 自审 + 人工审查）**

```
请对本次修改做代码审查，不要继续写代码。
按下面结构审查：
1. 自审：是否只改了计划内文件 / 有无无关重构 / 有无新增依赖 / 有无误删旧逻辑
2. 边界条件：空数据 / 接口失败 / 未登录 / 权限不足 / 重复点击 / 移动端
3. 安全：是否暴露密钥 token / 权限判断缺失 / 输入未校验 / 接口鉴权
4. 删除内容：删了什么、为什么、有没有别处依赖
5. 业务逻辑：是否符合需求、异常路径、是否影响旧规则
最后给出结论：可以继续 / 需要小修 / 需要回退部分 / 需要重新计划。
```

### 第 20 章 变现核心逻辑

> 难度：入门 ｜ 更新时间：2026-08-14
>
> **大白话讲**：AI 变现三种层级——卖时间（接单）、卖成果（产品）、卖系统（资产）；判断值不值得做的标准只有一个：你的时薪。

#### 为什么 2026 年仍是普通人最好的入场时机

1. **工具零代码化**：Coze（扣子）、Dify、n8n 让"会说话就能搭 Agent"成为现实；
2. **企业付费意愿觉醒**：中小企业老板知道 AI 能省钱，但他们不会用——这正是你的机会；
3. **协议普及**：MCP + A2A 双协议让 Agent 能跨软件、跨智能体协作，功能边界大幅扩展；
4. **政策红利**：《数字经济促进法》实施细则明确支持低门槛数字服务岗位。

#### 三种变现层级

| 层级 | 本质 | 月收入预期 |
|------|------|-----------|
| 第一层：接单型（卖时间） | 用 AI 提高效率，接更多单 | 1,000–10,000 元 |
| 第二层：产品型（卖成果） | 把 AI 能力打包成标准化服务/产品 | 5,000–30,000 元 |
| 第三层：资产型（卖系统） | 搭建自动运行的 AI 系统，睡后收入 | 10,000–100,000+ 元 |

普通人从第一层起步，跑通一个行业后向第二、三层升级。

#### 通用算账公式

```
你的时薪 = 客单价 ÷ 你实际投入的时间
AI 的价值 = （原人工耗时 - 现 AI 耗时）× 你的时薪
接单标准：时薪 ≥ 50 元/小时（兼职）或 ≥ 100 元/小时（全职）
```

举例：公众号推文人工 4 小时，AI 初稿 + 人工润色 1 小时，省 3 小时。收费 200 元/篇、投入 1 小时 → 时薪 200 元，值得做。

> **说白了就是**：AI 不是印钞机，是杠杆——放大你的时间、判断力和交付质量。

5. **不做私域**：平台随时封号改规则，客户必须沉淀到微信/公众号/社群。

#### 五条铁律

1. **当实习生，不当神**：能解决大多数问题，但不能解决所有问题，需要你引导、限制、验收；
2. **权限最小化**：不要开"完全访问"——就像把电脑密码给朋友，他"好心"删了你的文件你还不知道。沙盒模式选"请求批准"，`danger-full-access` 新手禁用；
3. **重要操作先备份**：批量改文件前先列改动清单，或先 Git 提交；
4. **关键结果人工验收**：代码、文案、数据上线前自己过一遍；
5. **敏感信息别喂给它**：身份证、密码、密钥、客户隐私，默认它"记不住"也不该知道。

#### 检查 Skill / 插件是否含恶意代码（五步）

1. **看来源**：只从官方市场、作者官方仓库、高 star 且近期活跃的 GitHub 仓库下载；QQ 群文件、网盘分享要警惕；
2. **看内容**：重点找——下载并执行远程代码的命令（curl/wget 管道执行）、读取敏感文件（浏览器 cookie、SSH 密钥、~\.ssh）、上传数据的代码、base64 混淆长串；
3. **看权限声明**：好的 Skill 会写明"需要什么权限、为什么需要"；不声明就索要权限的要警惕；
4. **小范围先试**：先在无敏感数据的测试项目里跑一遍，观察行为；
5. **汉化包/修改版警惕**：官方语言包优先（第三方汉化包可能藏恶意代码）。

#### 关于"后门"与破解版工具

- 原教程提醒：**Claude Code 2.1.91–2.1.196 被社区报告存在后门风险**——只从官方渠道安装、保持最新版本（`npm update -g @anthropic-ai/claude-code`）；
- 一切"破解版""魔改版""带梯子版"安装包都有植入风险，别图省事；
- "绕封锁安装""接码注册"涉及账号服务条款和所在地法律法规，**本教程仅作信息说明，不推荐、不教学**，请使用官方支持的正规渠道。

#### 网络与中转风险

- 部分海外工具在部分地区不可直接访问，是否使用、如何访问请自行判断并遵守所在地法律法规；
- **不建议用中转站**：虚标、降智、跑路是常态；若必须用，选有信誉、标明上游的服务，且**不要用中转站处理敏感数据**；
- API Key 像银行卡密码一样保管：泄露可能被刷爆账单，用量异常立即检查/重置。

#### 本地模型的安全优势

数据不出本机，适合隐私敏感内容；但本地模型能力弱于云端旗舰——别用 7B 模型做复杂推理然后骂它笨；模型只从官方库（ollama.com/library）拉取。

#### 危险命令红线（看到先喊停）

| 命令/操作 | 风险 |
|----------|------|
| `rm -rf`、`del /s`、`rd /s`、`Remove-Item -Recurse` | 批量删除文件/目录 |
| `git reset --hard`、`git clean -fd` | 丢失未提交改动 |
| `curl xxx ｜ sh` / `iex` 远程脚本 | 下载并直接执行未知代码 |
| `--yolo`、`danger-full-access`、跳过审批参数 | 放开全部权限 |
| `sudo` | 修改系统级内容 |

应对：先让它解释"这条命令的作用、风险、有没有更安全的替代方案"；全局 AGENTS.md 里可以直接写死"禁止批量删除，只能一次删一个明确路径的文件"。

> **带走这句话**：把智能体关进围栏（沙盒+审批），把 Skill 当陌生人审，把 Key 当密码管。

## 附录 C：常见报错速查表

安装和使用智能体时最常见的报错，按 Ctrl+F 搜关键词。

| 报错关键词 | 原因 | 解决方法 |
|---|---|---|
| command not found / 不是内部命令 | 软件没装好或 PATH 没配 | 重装该软件，装完**关掉旧终端、开新窗口**再试 |
| 禁止运行脚本 / Execution Policy | Windows PowerShell 默认禁止脚本 | 管理员开 PowerShell，输入 `Set-ExecutionPolicy RemoteSigned`，输 Y |
| npm ERR / EACCES / permission denied | 权限不够 | 管理员身份开终端再装；或用 `npm config set prefix` 改到用户目录 |
| Authentication failed / 401 | API KEY 错了或过期 | 回平台重新复制 Key，检查多余空格；确认 Key 没写在引号里 |
| Rate limit / 429 | 调用太频繁，触发限速 | 等 1 分钟再试；免费额度用完需充值或换平台 |
| Connection refused / ECONNREFUSED | 本地服务没启动 | 检查 Ollama 等本地服务是否在运行（`ollama ps`） |
| base_url 错误 / model not found | Base URL 格式错或模型名写错 | Base URL 结尾必须是 `/v1`；模型名去平台文档复制，别手打 |
| token 不足 / context too long | 对话太长超出上下文窗口 | 输入 `/compact` 压缩对话；或开新会话 |
| Python / pip 不是内部命令 | Python 安装时没勾 Add to PATH | 重装 Python，勾选 **Add Python to PATH**；或手动加 PATH |

> 90% 的安装问题都能解决：把**完整报错信息**复制粘贴给智能体，问它"我是新手，请用大白话解释这个报错并告诉我怎么解决"。
